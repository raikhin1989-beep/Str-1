# Эксплуатация

Как выкатывать, как проверять, как чинить. Подробный разбор аварий появится
в `docs/RUNBOOK.md` на шаге 11 — здесь база, которая нужна с первого дня.

## Выкат

Пуш в `main` с изменениями в `site/**`, `app/**` или самого workflow запускает
деплой. Коммиты, которые правят только `docs/**`, деплой не запускают —
это сделано намеренно, чтобы правка документации не трогала работающий сайт.

Ручной запуск: Actions → Deploy → Run workflow. Там же действие `inspect` —
только чтение: состояние служб, портов, диска, сертификата. Ничего не меняет.

## Проверка, что выкат доехал

```
curl https://raikhinwhiskey.duckdns.org/version   # SHA последнего коммита
curl https://raikhinwhiskey.duckdns.org/healthz   # ok
curl http://<SERVER_HOST>:8081/version            # тот же SHA
```

SHA пишется **последним шагом** деплоя, уже после выкладки файлов, перезапуска
приложения и проверки снаружи. Поэтому свежий SHA означает «прогон дошёл до
конца», а не «файлы скопировались». Устаревший SHA — прогон упал или ещё идёт.

Оба входа обязаны показывать одинаковый SHA: они читают один докрут, расхождение
означает, что один из двух Caddy отдаёт устаревшее.

Дополнительно, когда появится приложение (шаг 1):

```
curl https://raikhinwhiskey.duckdns.org/api/health   # {"status":"ok"}
```

## Службы на сервере

| Служба | Что делает | Как посмотреть |
| --- | --- | --- |
| `str-1-app.service` | Приложение, uvicorn на `127.0.0.1:8082` | `systemctl status str-1-app`, `journalctl -u str-1-app -n 100` |
| `str-1-site.service` | Наш Caddy на 8081, запасной вход | `systemctl status str-1-site` |
| `caddy.service` | Основной Caddy соседа, 80 и 443 | `systemctl status caddy` |

Приложение упало, а сайт нужен прямо сейчас — убрать `reverse_proxy` из
`/etc/caddy/str-1.caddyfile` и `/etc/caddy/sites.d/str-1.caddy`, перезагрузить
Caddy: вернётся статика. Следующий деплой перепишет конфиги обратно.

## Бэкапы базы

База — один файл `/var/lib/str-1/app.db`. Правила:

* ежедневная копия в `/var/backups/str-1/app-YYYY-MM-DD.db`, хранится 14 последних;
* копия снимается через `sqlite3 .backup`, а не `cp`: при включённом WAL простое
  копирование файла может дать битую копию;
* перед каждым деплоем, который меняет схему, снимается внеочередная копия;
* в админке есть кнопка «скачать бэкап» — перед дегустацией имеет смысл нажать
  и сохранить файл себе.

Восстановление: остановить `str-1-app`, положить копию на место `app.db`
(удалив рядом `app.db-wal` и `app.db-shm`), запустить службу.

**Базы нет в репозитории и не будет.** В ней имена участников и их ответы — это
их данные, а не содержимое сайта.

## Секреты

Settings → Secrets and variables → Actions. Список и назначение — в
`docs/ARCHITECTURE.md`. Правила:

* значения секретов не выводятся в логи никогда, только факт наличия и длина;
* необязательный секрет отсутствует — соответствующая функция выключается
  с предупреждением, деплой не падает;
* секреты этого репозитория отдельные от секретов соседнего `Str`, даже если
  указывают на ту же машину.

## Чего нельзя делать

Сервер общий. Никогда:

* не редактировать `/etc/caddy/Caddyfile` — сосед перезаписывает его на каждом
  своём деплое, правка исчезнет, а до того может сломать ему выкат;
* не писать в `/var/www/html`;
* не занимать порты 80 и 443;
* не класть ничего своего в `/var/www/str-1`, кроме того, что приходит из `site/`:
  докрут синхронизируется с `--delete`.

Наш файл `/etc/caddy/sites.d/str-1.caddy` попадает в конфигурацию соседа через
`import`. Поэтому ошибка в нём ломает **его** деплой — валидация объединённой
конфигурации выполняется до перезагрузки, и при провале файл удаляется обратно.
