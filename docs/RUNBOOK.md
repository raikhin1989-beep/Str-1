# Что делать, когда что-то сломалось

Инструкция для человека, а не для агента. Написана так, чтобы починить можно
было с телефона, стоя в комнате с гостями. Команды выполняются по SSH на том же
сервере (`ssh root@<SERVER_HOST>`).

Сначала — три вопроса, которые отвечают почти на всё:

```
curl -s https://raikhinwhiskey.duckdns.org/version    # какой коммит выложен
curl -s https://raikhinwhiskey.duckdns.org/healthz    # -> ok, файл на диске
curl -s https://raikhinwhiskey.duckdns.org/api/health # -> json, живо приложение
```

* `healthz` отвечает, а `api/health` — нет → жив Caddy, упало приложение;
* оба молчат → дело в Caddy, домене или сети;
* `version` показывает старый коммит → последний деплой не дошёл до конца.

---

## Сайт не открывается по домену

Запасной вход работает всегда и ни от чего не зависит:

```
http://<SERVER_HOST>:8081/
```

Раздайте гостям его — вечер продолжится. Дальше разбирайтесь спокойно.

Домен обслуживает **основной** Caddy, общий с соседним проектом `Str`.

```
systemctl status caddy            # жив ли основной
caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
grep -r import /etc/caddy/Caddyfile
```

Последняя строка — главное. В конце файла соседа должно быть
`import /etc/caddy/sites.d/*.caddy`. Если строки нет, деплой соседа затёр её:
наш блок лежит в `/etc/caddy/sites.d/str-1.caddy`, но не подключается. Верните
строку и перезагрузите: `systemctl reload caddy`.

Сертификат: `journalctl -u caddy | grep -i certificate`. Если Let's Encrypt
ругается на DNS — проверьте, что DuckDNS указывает на нужный адрес:
`curl -s "https://www.duckdns.org/update?domains=raikhinwhiskey&token=<TOKEN>&ip="`.

## Приложение упало

```
systemctl status str-1-app
journalctl -u str-1-app -n 100 --no-pager
systemctl restart str-1-app
```

Гости в это время видят не белый экран, а запасную страницу «Секунду» — её
отдаёт Caddy из `/var/www/str-1/index.html`. Личные ссылки и ответы никуда
не делись: они в базе.

Если приложение не поднимается после перезапуска, чаще всего виновата
последняя миграция или переменная окружения:

```
ls -la /etc/str-1/app.env          # права должны быть 640, владелец root:str1
/opt/str-1/venv/bin/python -c "from app.main import app; print('импорт ок')"
```

## Бот молчит

```
curl -s "https://api.telegram.org/bot<TOKEN>/getWebhookInfo"
```

Смотрите поля `url` и `last_error_message`. Частые случаи:

* `url` пустой → вебхук слетел, перезапустите деплой (он ставит его заново);
* `last_error_message` про сертификат → чинится вместе с доменом, см. выше;
* `pending_update_count` растёт → приложение не отвечает на вебхук, см. выше.

**С этого сервера исходящие к `api.telegram.org` не проходят** — проверено
на выкате 1 августа: `curl` к API отваливается по таймауту, хотя тот же запрос
с раннера GitHub проходит. Что из этого следует:

* **привязка работает**: телеграм сам стучится к нам вебхуком, входящие идут;
* **подтверждение «Готово, имя!» не приходит** — его шлём мы, а исходящие не идут.
  Гость видит привязку, вернувшись на свою страницу;
* **кнопка «Разослать итоги» бессильна**: в отчёте все окажутся в «не дошло».
  На странице итогов в админке есть готовый текст — скопируйте и отправьте
  в общий чат руками, ссылка на разбор там же.

**Как всё-таки разослать итоги.** Рассылку везёт GitHub — у раннера доступ
к телеграму есть:

1. Actions → **Deploy to server** → Run workflow;
2. действие — **broadcast**;
3. в логе будет «отправлено: N, не дошло: M».

Раннер забирает готовые сообщения у сайта (`/internal/outbox/<секрет вебхука>`),
отправляет их и сообщает обратно, что дошло. Отметка о доставке ставится только
по этому докладу, поэтому повторный запуск никому не пришлёт дважды, а тем, кому
не дошло, — догонит.

Совсем без телеграма вечер тоже заканчивается: ссылка `/results/<код>` работает
у всех, а на странице итогов в админке есть готовый текст для чата.

Если бот не пишет конкретному человеку — он не нажал «Старт» у бота или
заблокировал его. Кнопку «Разослать итоги» можно нажать ещё раз: тем, кому
дошло, второй раз не придёт.

## Сайт отвечает «Internal Server Error» на всё, что трогает базу

Проверьте границу: откройте `/` и `/api/health` — если они живы, а
`/whisky?q=aberlour` и страница гостя падают, дело не в базе как таковой.

Так это выглядело 5 августа. В журнале было:

```
sqlite3.OperationalError: unable to open database file
... [Errno 24] Too many open files
```

**У процесса кончились файловые дескрипторы.** Приложение перестаёт открывать
что бы то ни было: базу, сокет наружу, даже шаблон страницы ошибки — поэтому
вместо оформленной страницы приходит голое «Internal Server Error».

Немедленно:

```
systemctl restart str-1-app
```

Данные при этом целы: они в `app.db`, а не в памяти процесса.

Причина была в `with sqlite3.connect(...)`: он фиксирует транзакцию, но
соединение не закрывает — это делает сборщик мусора, когда дойдут руки.
Починено в `app/db.py` (соединение закрывается вместе с блоком `with`),
и службе поднят `LimitNOFILE`. Если подобное повторится, смотрите, сколько
дескрипторов держит процесс:

```
PID=$(systemctl show -p MainPID --value str-1-app)
ls /proc/$PID/fd | wc -l
grep -i "open files" /proc/$PID/limits
```

## Где посмотреть, что упало

**Админка → «Сбои».** Тип ошибки, страница и место в коде — свежие сверху.
Заведено после живого теста, где «Internal Server Error» был, а узнать
о нём было неоткуда.

Туда попадают только настоящие сбои. «Страницы нет» и «сейчас раунд не идёт» —
обычные ответы, а не поломки, и список ими не засоряется. Пустой список
означает, что приложение не падало ни разу.

Полная трасса по-прежнему в журнале службы:
`journalctl -u str-1-app -n 100 --no-pager`.

## «Нажал Старт, а привязки нет»

Смотрите по порядку — ответ будет на первом же шаге, где что-то не так.

1. **Админка → Телеграм.** Там журнал того, что реально пришло от бота:
   * `привязка` — всё сработало, обновите страницу дегустации;
   * `Старт без кода` — человек **нашёл бота в поиске и написал ему сам**.
     Так не работает: код привязки зашит в кнопку «Привязать телеграм» на
     личной странице гостя, и открывать надо именно её;
   * `чужой код` — ссылка от прошлой дегустации, гостю нужна свежая;
   * `отказ` — постучались не нашим секретом, это не наш телеграм;
   * **пусто** — телеграм до нас не доходит, идите к пункту 2.
2. **Actions → Deploy to server → Run workflow → действие `telegram`.**
   Спросит у самого телеграма: зарегистрирован ли вебхук, сколько обновлений
   ждут доставки и какая была последняя ошибка. Адрес вебхука не печатается —
   в нём секрет.
3. Если вебхук не зарегистрирован — запустите обычный деплой, он ставит его
   заново на каждом прогоне.

**Самый надёжный способ, если кнопка не сработала:** на странице гостя,
под кнопкой, есть его личный код. Пусть отправит этот код боту одним
сообщением — бот принимает и так. Это спасает в самом частом случае: гость
уже запускал бота раньше (например, на репетиции), телеграм по ссылке
открывает старый диалог и `/start` с кодом сам не отправляет. Кнопка при
этом выглядит нажатой, а привязки нет.

Помните: **ответного сообщения бот не пришлёт** — исходящие с сервера
не проходят. Привязку показывает страница гостя: она сама заметит её
в течение трёх секунд и перерисуется. Видно её и в админке, в таблице гостей.

## Гость уже был на прошлой дегустации

Телеграм ему привязывать заново не нужно:

* **с того же телефона** — имя и контакт подставятся сами, привязка перенесётся
  автоматически. Основание — тот же браузер, который открывал прошлую запись;
* **с другого телефона** — в админке, в колонке «Телеграм», появится кнопка
  «перенести с «<дегустация>»», если контакт совпал с прошлым разом. Нажимаете
  вы, а не программа: контакт пишет сам гость, и по строчке связывать нельзя —
  иначе итоги уехали бы тому, чей ник вписали по ошибке.

## Гость потерял свою ссылку

Самая частая беда вечера. Три пути, по порядку:

1. **С его телефона** — открыть главную сайта. Тот же браузер помнит страницу
   тридцать дней и предложит «С возвращением, имя»;
2. **из админки** — страница дегустации, таблица гостей, колонка «Личная
   ссылка». Нажать на поле — выделится целиком; ссылка «QR» открывает код
   на весь экран, его можно показать гостю с телефона;
3. **прислать** — если гость оставил контакт при регистрации, он тут же,
   в колонке «Куда прислать».

Ссылка — это пропуск на чужую страницу: чужую не показывайте и в общий чат
не кидайте.

## Фото этикетки не распознаётся

В ответе гостю написано «Чтение этикетки (Yandex Vision OCR) отвечает
«нет доступа»» — значит 403, и чинится это в консоли Yandex Cloud, не в коде.
Нужны **две разные вещи**, и обе сразу:

| Что | Где | Кому |
| --- | --- | --- |
| роль `ai.vision.user` | каталог → «Права доступа» → «Назначить роли» | сервисному аккаунту, которому принадлежит ключ |
| область действия `yc.ai.vision.execute` | задаётся при **создании** API-ключа | самому ключу |

Роль даёт право аккаунту, область разрешает ключу этим правом пользоваться.
Одного без другого не хватает.

Область действия после создания **не меняется** — ключ с неподходящей
областью выпускается заново. Текстовой модели нужна своя область,
`yc.ai.languageModels.execute`, так что у ключа их две; если выпускаете новый
ключ — задайте обе, иначе вместе с фото отвалится и поиск по названию.
Срок действия ключу не ставьте: он истечёт посреди вечера и будет выглядеть
как поломка.

Проверить, не трогая сайт (ключ в консоль не выводите):

```
read -rs YKEY
curl -s -o /dev/null -w '%{http_code}\n' \
  -X POST https://ocr.api.cloud.yandex.net/ocr/v1/recognizeText \
  -H "Authorization: Api-Key $YKEY" -H "x-folder-id: <FOLDER_ID>" \
  -H 'Content-Type: application/json' \
  -d '{"mimeType":"JPEG","languageCodes":["*"],"model":"page","content":"/9j/4AAQSkZJRg=="}'
```

`400` — права в порядке, ругань только на заведомо битую картинку из примера.
`403` — прав всё ещё нет. `401` — ключ не тот.

**Секрет для этого трогать не нужно.** Сайт сам спрашивает у Vision OCR,
пускает ли тот его, и показывает кнопку по ответу: выдали роль в консоли —
кнопка появится сама в течение пяти минут, без выката. Отозвали — так же
исчезнет. Проверить, что видит сайт:

```
curl -s https://raikhinwhiskey.duckdns.org/api/health   # поле ai_photo
journalctl -u str-1-app | grep -i 'Vision OCR'         # и почему именно так
```

`AI_PHOTO` остался ручным переопределением на два редких случая: `on` —
показать кнопку вопреки отказу, чтобы увидеть настоящую ошибку вместо
спрятанной кнопки; `off` — спрятать её там, где всё работает. Деплой
проверяет согласованность: если секрет включён, а приложение фото
не предлагает, выкат падает с ошибкой, а не делает вид, что всё хорошо.

## «Не могу записаться» / «черновик не сохраняется»

Ограничения частоты. Важно понимать, **чем они считают**: вся компания сидит
за одним роутером, и снаружи это один адрес.

| Что | Чем считается | Потолок |
| --- | --- | --- |
| регистрация | адрес | 60 за 10 минут |
| черновик раунда | личная ссылка гостя | 240 за 10 минут |
| вопрос про виски у ИИ | адрес | 60 в час |

Регистрация и вопросы к ИИ — на всю компанию сразу: это цена того, что до
записи человека ещё нечем опознать. Потолки подняты так, чтобы в них свободно
помещался стол на два десятка человек; упереться можно только потоком.
Черновик считается по личной ссылке, поэтому один увлёкшийся гость больше
не отключает автосохранение всему столу.

Счётчики живут в памяти процесса: `systemctl restart str-1-app` обнуляет их
мгновенно. Ответы и черновики при этом не теряются — они в базе.

## Нужно откатить

```
cd /opt/str-1/app && git log --oneline -5     # версии в репозитории, не на сервере
```

На сервере лежит только выложенный код, истории там нет. Откат делается
через GitHub: `git revert <коммит>` в `main`, деплой выложит предыдущее
поведение. Так быстрее и честнее, чем править файлы на боевой машине.

Совсем аварийный вариант, если GitHub недоступен: выключить проксирование,
оставив запасную страницу.

```
systemctl stop str-1-app
```

Сайт покажет «Секунду», данные останутся целы.

## База повреждена

Сначала убедитесь, что дело в ней:

```
/opt/str-1/venv/bin/python - <<'PY'
import sqlite3
print(sqlite3.connect("/var/lib/str-1/app.db").execute("PRAGMA integrity_check").fetchone())
PY
```

Ответ `ok` означает, что база цела и проблема в другом.

Восстановление из копии:

```
ls -la /var/backups/str-1/            # копии за последние 14 дней
systemctl stop str-1-app
cp /var/lib/str-1/app.db /var/lib/str-1/app.db.broken      # сначала сохраняем как есть
gunzip -c /var/backups/str-1/app-<дата>.db.gz > /var/lib/str-1/app.db
chown str1:str1 /var/lib/str-1/app.db
systemctl start str-1-app
```

`app.db.broken` не удаляйте: из повреждённой базы часто удаётся достать
последние ответы, а из копии они уже потеряны.

Свежую копию можно снять в любой момент — в админке есть «Скачать бэкап»,
он делает слепок на текущую минуту.

## Перед вечером: короткая проверка

За полчаса до гостей, по порядку:

1. `curl -s https://raikhinwhiskey.duckdns.org/api/health` — все флаги `true`,
   какие ожидаете (`admin`, `telegram`, `ai`);
2. откройте `/admin`, зайдите паролем;
3. состав дегустации на месте, номера перемешаны;
4. откройте ссылку регистрации со **своего телефона** и запишитесь тестовым
   гостем — потом удалять не нужно, он просто останется в таблице с нулём;
5. привяжите телеграм этому тестовому гостю — проверяется вся цепочка бота;
6. нажмите «Скачать бэкап» — файл должен скачаться;
7. откройте `/board/<код>` на том экране, который будете показывать.

Пункт 4 важнее прочих: он проверяет то же, что будут делать гости, тем же
способом, что и они.

## Куда смотреть, если непонятно

```
journalctl -u str-1-app -f          # приложение, живой поток
journalctl -u str-1-site -n 50      # наш Caddy на 8081
journalctl -u caddy -n 50           # общий Caddy, домен и сертификаты
journalctl -u str-1-backup -n 20    # ежедневный бэкап
```

Действия админа пишутся в саму базу, таблица `audit_log`:

```
/opt/str-1/venv/bin/python - <<'PY'
import sqlite3
conn = sqlite3.connect("/var/lib/str-1/app.db")
for row in conn.execute("SELECT at, ip, action, details FROM audit_log ORDER BY id DESC LIMIT 20"):
    print(*row, sep=" | ")
PY
```
