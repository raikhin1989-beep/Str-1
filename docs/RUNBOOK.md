# Что делать, когда что-то сломалось

Инструкция для человека, а не для агента. Написана так, чтобы починить можно
было с телефона, стоя в комнате с гостями. Команды выполняются по SSH на том же
сервере (`ssh root@<SERVER_HOST>`).

Сначала — три вопроса, которые отвечают почти на всё:

```
curl -s https://raikhinwhiskey.duckdns.org/version    # какой коммит выложен
curl -s https://raikhinwhiskey.duckdns.org/healthz    # -> ok, файл на диске
curl -s https://raikhinwhiskey.duckdns.org/api/health # -> json, живо приложение
```

* `healthz` отвечает, а `api/health` — нет → жив Caddy, упало приложение;
* оба молчат → дело в Caddy, домене или сети;
* `version` показывает старый коммит → последний деплой не дошёл до конца.

---

## Сайт не открывается по домену

Запасной вход работает всегда и ни от чего не зависит:

```
http://<SERVER_HOST>:8081/
```

Раздайте гостям его — вечер продолжится. Дальше разбирайтесь спокойно.

Домен обслуживает **основной** Caddy, общий с соседним проектом `Str`.

```
systemctl status caddy            # жив ли основной
caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
grep -r import /etc/caddy/Caddyfile
```

Последняя строка — главное. В конце файла соседа должно быть
`import /etc/caddy/sites.d/*.caddy`. Если строки нет, деплой соседа затёр её:
наш блок лежит в `/etc/caddy/sites.d/str-1.caddy`, но не подключается. Верните
строку и перезагрузите: `systemctl reload caddy`.

Сертификат: `journalctl -u caddy | grep -i certificate`. Если Let's Encrypt
ругается на DNS — проверьте, что DuckDNS указывает на нужный адрес:
`curl -s "https://www.duckdns.org/update?domains=raikhinwhiskey&token=<TOKEN>&ip="`.

## Приложение упало

```
systemctl status str-1-app
journalctl -u str-1-app -n 100 --no-pager
systemctl restart str-1-app
```

Гости в это время видят не белый экран, а запасную страницу «Секунду» — её
отдаёт Caddy из `/var/www/str-1/index.html`. Личные ссылки и ответы никуда
не делись: они в базе.

Если приложение не поднимается после перезапуска, чаще всего виновата
последняя миграция или переменная окружения:

```
ls -la /etc/str-1/app.env          # права должны быть 640, владелец root:str1
/opt/str-1/venv/bin/python -c "from app.main import app; print('импорт ок')"
```

## Бот молчит

```
curl -s "https://api.telegram.org/bot<TOKEN>/getWebhookInfo"
```

Смотрите поля `url` и `last_error_message`. Частые случаи:

* `url` пустой → вебхук слетел, перезапустите деплой (он ставит его заново);
* `last_error_message` про сертификат → чинится вместе с доменом, см. выше;
* `pending_update_count` растёт → приложение не отвечает на вебхук, см. выше.

**С этого сервера исходящие к `api.telegram.org` не проходят** — проверено
на выкате 1 августа: `curl` к API отваливается по таймауту, хотя тот же запрос
с раннера GitHub проходит. Что из этого следует:

* **привязка работает**: телеграм сам стучится к нам вебхуком, входящие идут;
* **подтверждение «Готово, имя!» не приходит** — его шлём мы, а исходящие не идут.
  Гость видит привязку, вернувшись на свою страницу;
* **кнопка «Разослать итоги» бессильна**: в отчёте все окажутся в «не дошло».
  На странице итогов в админке есть готовый текст — скопируйте и отправьте
  в общий чат руками, ссылка на разбор там же.

**Как всё-таки разослать итоги.** Рассылку везёт GitHub — у раннера доступ
к телеграму есть:

1. Actions → **Deploy to server** → Run workflow;
2. действие — **broadcast**;
3. в логе будет «отправлено: N, не дошло: M».

Раннер забирает готовые сообщения у сайта (`/internal/outbox/<секрет вебхука>`),
отправляет их и сообщает обратно, что дошло. Отметка о доставке ставится только
по этому докладу, поэтому повторный запуск никому не пришлёт дважды, а тем, кому
не дошло, — догонит.

Совсем без телеграма вечер тоже заканчивается: ссылка `/results/<код>` работает
у всех, а на странице итогов в админке есть готовый текст для чата.

Если бот не пишет конкретному человеку — он не нажал «Старт» у бота или
заблокировал его. Кнопку «Разослать итоги» можно нажать ещё раз: тем, кому
дошло, второй раз не придёт.

## Нужно откатить

```
cd /opt/str-1/app && git log --oneline -5     # версии в репозитории, не на сервере
```

На сервере лежит только выложенный код, истории там нет. Откат делается
через GitHub: `git revert <коммит>` в `main`, деплой выложит предыдущее
поведение. Так быстрее и честнее, чем править файлы на боевой машине.

Совсем аварийный вариант, если GitHub недоступен: выключить проксирование,
оставив запасную страницу.

```
systemctl stop str-1-app
```

Сайт покажет «Секунду», данные останутся целы.

## База повреждена

Сначала убедитесь, что дело в ней:

```
/opt/str-1/venv/bin/python - <<'PY'
import sqlite3
print(sqlite3.connect("/var/lib/str-1/app.db").execute("PRAGMA integrity_check").fetchone())
PY
```

Ответ `ok` означает, что база цела и проблема в другом.

Восстановление из копии:

```
ls -la /var/backups/str-1/            # копии за последние 14 дней
systemctl stop str-1-app
cp /var/lib/str-1/app.db /var/lib/str-1/app.db.broken      # сначала сохраняем как есть
gunzip -c /var/backups/str-1/app-<дата>.db.gz > /var/lib/str-1/app.db
chown str1:str1 /var/lib/str-1/app.db
systemctl start str-1-app
```

`app.db.broken` не удаляйте: из повреждённой базы часто удаётся достать
последние ответы, а из копии они уже потеряны.

Свежую копию можно снять в любой момент — в админке есть «Скачать бэкап»,
он делает слепок на текущую минуту.

## Перед вечером: короткая проверка

За полчаса до гостей, по порядку:

1. `curl -s https://raikhinwhiskey.duckdns.org/api/health` — все флаги `true`,
   какие ожидаете (`admin`, `telegram`, `ai`);
2. откройте `/admin`, зайдите паролем;
3. состав дегустации на месте, номера перемешаны;
4. откройте ссылку регистрации со **своего телефона** и запишитесь тестовым
   гостем — потом удалять не нужно, он просто останется в таблице с нулём;
5. привяжите телеграм этому тестовому гостю — проверяется вся цепочка бота;
6. нажмите «Скачать бэкап» — файл должен скачаться;
7. откройте `/board/<код>` на том экране, который будете показывать.

Пункт 4 важнее прочих: он проверяет то же, что будут делать гости, тем же
способом, что и они.

## Куда смотреть, если непонятно

```
journalctl -u str-1-app -f          # приложение, живой поток
journalctl -u str-1-site -n 50      # наш Caddy на 8081
journalctl -u caddy -n 50           # общий Caddy, домен и сертификаты
journalctl -u str-1-backup -n 20    # ежедневный бэкап
```

Действия админа пишутся в саму базу, таблица `audit_log`:

```
/opt/str-1/venv/bin/python - <<'PY'
import sqlite3
conn = sqlite3.connect("/var/lib/str-1/app.db")
for row in conn.execute("SELECT at, ip, action, details FROM audit_log ORDER BY id DESC LIMIT 20"):
    print(*row, sep=" | ")
PY
```
